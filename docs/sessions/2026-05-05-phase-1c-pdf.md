# Phase 1c — PDF upload + extraction

*Session date: 2026-05-05 · Topic: Phase 1c — PDF ingestion via pymupdf, reusing the 1b extraction pipeline*

## Decision

Drop a broker teaser or CIM PDF into the existing `/listings/new` extract panel. Server parses with `pymupdf` (a.k.a. `fitz`), then runs the resulting text through the same `extract_listing()` call as Phase 1b. Same response shape, same form-population code path on the frontend.

No PDF storage, no OCR, no chunking — three deliberate "not yet" decisions:
- **Storage**: only the parsed text goes into `raw_text`. The binary is dropped after extraction. If we later want to re-extract against the original layout, we'll add a binary-store column.
- **OCR**: scanned/image-only PDFs raise `PDFParseError` with a clear "paste the text instead" message. OCR (tesseract / paddleocr) adds heavy deps; not justified until volume of scanned docs is real.
- **Chunking**: Sonnet 4.6's 200k context fits an 80-page CIM. If a 300-page document appears, the user will see the model handle it or fail informatively; we'll add chunking when reality forces it.

## Library choice — pymupdf, not pypdf

`pypdf` is simpler and dep-free, but layout extraction on multi-column or table-heavy CIMs produces garbage. `pymupdf` (built on MuPDF) does this correctly. AGPL license is a nonissue per charter §2 (single-user, never distributed, never publicly hosted) — the network-distribution clauses never trigger.

## Backend — what shipped

- Deps: `pymupdf==1.27.x`, `python-multipart==0.0.27`.
- `silvercurrent/ingestion/pdfs.py` — `extract_text_from_pdf(content: bytes) -> str` and `PDFParseError`. Uses `doc.load_page(i)` to iterate (mypy-friendlier than `for page in doc`) and joins page text with blank lines so the model can see structure.
- **Sparse-text guard**: `SPARSE_TEXT_THRESHOLD = 200`. Below that across the entire document, we assume the PDF is image-only and raise `PDFParseError` with an explicit "OCR isn't supported yet — try copy-pasting" hint. Tested.
- `Settings.pdf_max_bytes = 20_000_000` (20 MB). Most broker PDFs are 1–5 MB; 20 MB is generous.
- `POST /api/listings/extract-pdf` — `Annotated[UploadFile, File()]` pattern (dodges ruff B008). Validates: empty (400), over-cap (413), parse failure (400), extraction failure (502). Reuses `extract_listing()` so the JSON response is identical to `/extract`, which means the frontend's `applyExtraction()` works unchanged.
- 10 tests in `tests/test_pdf_extraction.py`. PDFs are synthesized in-memory via `pymupdf.open()` + `insert_textbox()` (the wrapping variant — `insert_text` runs off the page edge silently). No fixture files committed.
- All gates green: 36 backend tests pass, ruff check + format clean, mypy --strict clean (26 source files).

## Frontend — what shipped

- `apiPostMultipart<T>(path, FormData)` helper in `lib/api.ts`. Browser sets `Content-Type` with the boundary; we don't override it.
- `ListingForm` extract panel grows a third tab: **Upload PDF**. File `<Input type="file" accept="application/pdf,.pdf">` with filename + size displayed after selection. On Extract, builds `FormData`, POSTs to `/extract-pdf`, populates the form via the existing `applyExtraction()` path. PDF source is labeled `"pdf"` (rather than `"paste"`) so the inventory can later filter or sort on origin.
- `pnpm lint` + `pnpm build` green.

## Deviations / things to know

- **Empty-doc test removed.** pymupdf refuses to save a 0-page PDF (`ValueError: cannot save with zero pages`), so the defensive `page_count == 0` branch is unreachable from real bytes. The check stays in the parser as a guard against future loaders, but we don't unit-test it through the public API.
- **mypy hits on pymupdf.** `pymupdf` ships without typing stubs, so calls to `pymupdf.open`, `doc.close`, `doc.tobytes`, `doc.load_page`, and the `Rect` constructor get `# type: ignore[no-untyped-call]` annotations. Three in `pdfs.py`, four in the test helper. Cost: minor noise, contained.
- **`insert_text` vs. `insert_textbox`.** First test pass used `insert_text`, which positions text at a single coordinate and runs off the right edge silently — extracted text was tiny, sparse-text guard fired. Switched to `insert_textbox(rect, ...)` which wraps. Lesson worth noting if anyone writes more PDF-generating tests.
